# v2.1.0: Fixes from the September 2026 pilot

This document explains the changes in v2.1.0 for colleagues who test or build
on the extension. Each section describes what went wrong in the pilot, what was
changed, how it was verified, and what it means for the recorded data.

v2.1.0 is a **testing release**: it has passed the automated tests and a live
test on Amazon with a local build, but has not yet been submitted to the Chrome
Web Store. Participants still run v2.0.0.

All events from this version carry `schema_version = "4"`. Pilot data (v2.0.0)
has `schema_version = "3"`. Several measures are recorded differently (see
"Changes to the recorded data"), so the two versions should not be pooled
without accounting for that.

## Summary

| # | Problem in the pilot | Change |
|---|---|---|
| 1 | Re-taking the intake survey stopped the participant's session | A repeated link with the same participant ID keeps the original session |
| 2 | Quick product-page visits were not recorded | Product-page views and dwell time are recorded from the moment the page opens |
| 3 | Sort changes were never recorded; filter counts included non-filter clicks | Filter and sort actions are derived from the search URL |
| 4 | Two open tabs could make the sign-in state flip continuously | Signed in while any study tab shows the participant signed in |
| 5 | Two diagnostic events never reached the data | They are recorded before sign-in, as intended |
| 6 | The cart baseline was sometimes recorded twice | Recorded once per session |

## 1. Re-taking the intake survey no longer stops the session

**Pilot.** Several participants returned to the intake survey after reaching
Amazon and completed it again. Each new completion assigns a new condition and
product category, and the survey's new Amazon link carried that assignment.
The extension treated the mismatch as a different study session and stopped
recording. This accounted for most sessions that did not finish.

**Change** (`src/worker/StudyService.ts`). A link with the same participant ID
but a different condition, category or site now keeps the **first**
assignment. The study panel and the banner on the Amazon page show a notice
that the task has not changed and restate it. The ignored assignment is logged
once as `repeat_handoff_ignored`, so sessions where the participant may have
seen another condition's instructions can be identified. A link with a
*different* participant ID still stops the session, and that stop now also
writes a `session_summary`.

**Verified.** Unit tests; live test: pasting a second link with a different
condition and category during shopping left the session running with the
original assignment, showed the notice and logged one event.

## 2. Product-page views and dwell time on quick visits

**Pilot.** About one in five product-page visits had no `product_page_view`
and no dwell time, including pages where the participant added the product to
the cart. Amazon product pages keep loading for several seconds; the view was
only sent after the page had finished parsing and dwell timing only started
after the full page load, so participants who acted quickly were missed. The
mobile-style product URL `/gp/aw/d/<ASIN>` was not recognised at all.
Condition groups that browse faster lost more records, so the gap was not
random.

**Change.**
- `productAsin()` in `src/shared/StudyPolicy.ts` recognises `/dp/`,
  `/gp/product/` and `/gp/aw/d/` URLs.
- The content script sends `product_page_view` as soon as the study state is
  available, without waiting for the page to load. A page that Chrome
  prerenders in the background is only counted once it is actually shown.
- The service worker starts dwell timing when the navigation is committed and
  records one dwell row per page.

**Verified.** Unit tests; live test: a product added to the cart within about
two seconds of opening had its view and dwell recorded, and a `/gp/aw/d/` page
was recorded with its ASIN.

## 3. Filter and sort actions from the search URL

**Pilot.** No sort action was ever recorded: Amazon's sort menu does not fire
the event the extension listened for. The filter count included clicks on
"See more" (which only expands a list) and label fragments, and a throttle
dropped filters clicked in quick succession.

**Change** (`src/worker/Worker.ts`, `searchState()` in
`src/shared/StudyPolicy.ts`). Amazon applies filters and sorting by changing
the search-results URL, usually without reloading the page. The service worker
compares consecutive search URLs in each tab:

- a changed `s=` parameter is one **sort** action;
- a changed set of refinements (`rh=` tokens and custom price bounds) is one
  **filter** action, with the tokens `added` and `removed`;
- a new search query, back/forward navigation, and Amazon removing the search
  box's department scope (`i=aps`) are not filter actions.

The content script no longer sends `filter_used`; it passes the label of the
clicked filter (for example "Sony") to the service worker, which adds it as
`filter_text`.

**Verified.** Unit tests; replaying the pilot's navigation URLs through the new
logic gave 54 filter actions against 48 genuine filter clicks recorded (plus 7
expander or fragment clicks, now excluded), and 9 sort actions where none had
been recorded; live test: two filters, one "See more" and one sort change
produced exactly two filter actions and one sort action.

## 4. Sign-in state no longer flips between tabs

**Pilot.** In one session the sign-in state switched about ten times per second
for several minutes, producing over a thousand `amazon_login_confirmed` events,
flashing the sign-in prompt, and ending with the participant stopping the task.
A tab opened before signing in still showed "signed out"; each tab re-checked
on every state change and they overrode each other.

**Change** (`src/worker/Worker.ts`, `src/worker/StudyService.ts`). The service
worker keeps the last report from each tab and treats the participant as signed
in while any study tab shows them signed in. `amazon_login_confirmed` is sent
only for the first sign-in, which marks the start of the task.

**Verified.** Unit test reproducing the two-tab conflict (the previous code
flips the state repeatedly; the new code once); live test with a signed-out
tab kept open while signing in: one `amazon_login_confirmed`, no flicker.

## 5. Sign-in diagnostics are recorded

**Pilot.** `amazon_login_block_shown` and `pre_task_activity_suppressed`
describe what happens before sign-in, but were only sent after sign-in and were
not on the service worker's list of accepted events, so they were never
recorded.

**Change.** Both are sent during the shopping task before sign-in (other
conditions unchanged) and counted in `session_summary` as
`login_block_shown_count` and `pre_task_suppressed_count`.

**Verified.** Unit test; live test: the sign-in prompt shown in two tabs before
signing in was recorded twice.

## 6. One cart baseline per session

**Pilot.** Some sessions recorded `cart_baseline_count` twice within
milliseconds, when several tabs captured it at once.

**Change.** The service worker records only the first baseline of a session.

**Verified.** Unit test; one baseline in every live test run.

## Changes to the recorded data

| Event / field | v2.0.0 (pilot) | v2.1.0 |
|---|---|---|
| `schema_version` | `"3"` | `"4"` |
| `repeat_handoff_ignored` | – | New: `offered_arm`, `offered_category`, `offered_budget`, `offered_origin` |
| `amazon_login_confirmed` | On every sign-in state change | Once per session (task start) |
| `amazon_login_block_shown`, `pre_task_activity_suppressed` | Never recorded | Recorded; counts in `session_summary` |
| `product_page_view` | After page load; missed quick visits | When the page opens; includes `/gp/aw/d/` |
| `tab_dwell` | From full page load | From navigation commit; one row per page |
| `filter_used` | From clicks; `filter_type` always `refinement` | From URL changes (`source: "url"`); `filter_type` `refinement` (with `added`, `removed`) or `sort` (with `filter_value`) |
| `nav_committed` | All committed navigations | Prerendered pages flagged with `document_lifecycle: "prerender"` and not counted in `nav_count` |
| `cart_baseline_count` | Occasionally twice | Once per session |

## Testing these changes

A test with an unused participant ID covers all six fixes in one session:

1. Start signed out of Amazon. Open the intake-survey link to Amazon; the
   sign-in prompt appears (fix 5). Open a second Amazon tab, leave it signed
   out, then sign in from the first tab and keep both open (fix 4).
2. Search, apply two filters, click "See more" once, change the sort order,
   then press Back once (fix 3).
3. Open a product from the results and add it to the cart within about two
   seconds; then open `https://www.amazon.com/gp/aw/d/<ASIN>` (fix 2).
4. Open the intake-survey link again with a different condition and category
   (fix 1).

Expected: one `amazon_login_confirmed`, at least one
`amazon_login_block_shown`, two refinement and one sort `filter_used`, a
`product_page_view` and one `tab_dwell` for each product page, one
`cart_baseline_count`, one `repeat_handoff_ignored`, and the session still
running with the first assignment.

## Not yet addressed

- **Add-to-cart outside the product page.** Products added from the search
  results or from the assistant's product cards are not recorded as
  `add_to_cart_click` / `decision_made`. The final choice itself is recorded
  correctly.
- **Assistant product recommendations.** `assistant_text` records the
  conversation text but not the products the assistant recommends
  (`product_suggestions` is empty).
- **Text fields** such as `brand` and `title` are recorded as displayed by
  Amazon and need cleaning in analysis.
