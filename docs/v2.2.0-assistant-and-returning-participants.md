# v2.2.0: Returning participants, adds from any surface, and the assistant record

This document explains the changes in v2.2.0 for colleagues who test or build
on the extension. Each section describes what went wrong (in the September 2026
pilot or in the live tests since), what was changed, how it was verified, and
what it means for the recorded data.

v2.2.0 builds on v2.1.0 and has passed the automated tests and a series of live
tests on Amazon with a local build (all three study arms). It is the version
intended for the Chrome Web Store.

All events from this version carry `schema_version = "5"` (v2.1.0: `"4"`, pilot
v2.0.0: `"3"`). The assistant record in particular is structured differently
(see "Changes to the recorded data"); do not pool schema 5 with earlier data
without accounting for that.

## Summary

| # | Problem | Change |
|---|---|---|
| 1 | A participant who reopened the intake survey after reaching Amazon was assigned a new condition | The survey asks the extension for an existing session and sends the participant back to it |
| 2 | Adds to the cart from search results or the assistant were not recorded | Every add is recorded with the product and where it was added |
| 3 | Questions to the assistant were only visible inside conversation snapshots | Each question is recorded once, as asked or as an earlier conversation, including the product page's "Ask Alexa" box |
| 4 | Products the assistant recommends were not captured | Recommended products are recorded with title, price and, where Amazon provides it, ASIN |
| 5 | Assistant snapshots were 90% of all data and overstated assistant use | One snapshot per finished answer, without repetition; assistant use is measured by questions |

## 1. Returning participants keep their task

*Contributed in pull request #1 and extended in this release.*

**Problem.** Some pilot participants opened the intake survey again after
reaching Amazon. Qualtrics then assigned a new condition and product category,
while the extension kept the original task (v2.1.0), so the survey and the
extension disagreed and participants could get stuck.

**Change** (`lookupSession()` in `src/shared/StudyPolicy.ts`,
`src/worker/Worker.ts`). Before assigning a task, the intake survey can ask the
extension about this browser's study session. The extension answers without
changing anything it has stored. See "Intake survey lookup" below for the
message format.

The study panel also shows participants in both assistant arms where Amazon's
assistant is ("Amazon's AI shopping assistant is on the Amazon page, separate
from the study panel. You can open it there and type a question."). Only the
`chat` arm is told to use it. **This changes the `chat_no_guide` condition
compared with the pilot**, where that arm received no pointer to the assistant.

**Verified.** Unit tests for every lookup state; live test: a new participant
got `new`; after starting, the same ID got `resume` with the original Amazon
link, which continued the session without a `repeat_handoff_ignored`; a
different ID got `conflict`; the cue appeared in `chat` and `chat_no_guide`
and not in `classic`.

### Intake survey lookup

The survey page (any `*.qualtrics.com` page may message the extension) sends:

```js
chrome.runtime.sendMessage(EXTENSION_ID, { type: 'webmunk_lookup', prolificId }, reply => { ... });
```

| Reply | Meaning | Suggested survey action |
|---|---|---|
| `{ ok: true, status: 'new', version }` | No study session in this browser | Assign a task as usual |
| `{ ok: true, status: 'resume', url, version }` | Session in progress (or its registration failed and can be retried) | Send the participant to `url`, the original Amazon link |
| `{ ok: true, status: 'closed', stage, version }` | Session ended (`stage`: `final` = product confirmed, `done`, `stopped`) or passed its one-hour limit (`stage` still `shopping`) | `final`: send to the follow-up survey; otherwise ask the participant to contact the researcher |
| `{ ok: true, status: 'conflict', version }` | This browser holds a different participant's session | Do not continue; contact the researcher |
| `{ ok: false, error, version }` | Invalid participant ID | Check the ID |
| no reply (`chrome.runtime.lastError`) | Extension not installed, disabled, or older than v2.2.0 | Do not wait indefinitely: treat as unknown and continue with the normal flow |

`webmunk_ping` (installation check) is unchanged.

## 2. Adds to the cart from any surface

**Problem.** Products added from search-result tiles or from the assistant's
product cards produced no `add_to_cart_click` and no `decision_made`; only the
product page's own button was recorded.

**Change** (`src/content/Content.ts`, `src/worker/Worker.ts`). Adds are detected
from the cart count badge and attributed to the product of the last "Add to
cart" control clicked in the tab. The product page's button is still recorded
directly, and its badge increase is not counted again. Quantity changes on the
cart page do not count as adds.

Assistant product cards have no product link; their ASIN is read from the
card button's action ID (`asin_cards_<ASIN>_...`). Rows of comparison tables in
an answer carry `asin_cards_tbl_<ASIN>_...`, but Amazon has been seen giving
every row of a table the first row's ID. A table row's ASIN is therefore used
only when the table's rows carry distinct IDs; otherwise the add is recorded
without ASIN and with the row's product `title`. Offers from other shops
("Available from the Web") are not Amazon products and get no ASIN.

**Verified.** Unit tests; live tests: adds from a search tile, a product page,
an assistant card (with ASIN) and a comparison table row (with title) were
each recorded once with their surface; a quantity change was not recorded.

## 3. Questions to the assistant

**Problem.** The pilot record only contained periodic snapshots of the whole
conversation, so the number and timing of questions had to be reconstructed.
Amazon also shows earlier conversations again (from other pages, and from
before the study, on the participant's own account), which then looked like
new use. Questions asked in the product page's inline "Ask Alexa" box
("Looking for specific info?") were not recorded at all: that box answers in
place and the question never appears in the assistant panel.

**Change.**
- `assistant_query_submitted` is recorded once per question when it appears,
  with `via` (`typed` or `suggested`, i.e. one of Amazon's ready-made question
  buttons) and `surface` (`panel` or `inline_widget`).
- A question counts as asked only if the participant submitted it: Enter in the
  panel, its send button, or a ready-made question button. The submitted text
  is matched to the question that appears, so an earlier conversation that
  finishes loading after the submit cannot take its place.
- Question texts that appear without a submit (an earlier conversation shown
  again) are recorded once as `assistant_history_query` and do not count as
  use.
- The inline box's question is read when it is submitted (Enter, its button, or
  one of its question buttons, including follow-ups under an answer), never
  while being typed.

**Verified.** Unit and service-worker tests, including the exact sequence of a
live failure (an old conversation loading after the submit); live tests: typed
and ready-made questions in the panel and in the inline box were recorded once
each with the right `via` and `surface`, questions from an earlier conversation
were recorded only as history, and navigating or reloading recorded nothing
twice.

## 4. Recommended products

**Problem.** `product_suggestions` was always empty: the capture looked at the
card's button instead of the card, so every recommended product was skipped.

**Change.** Products are captured from the assistant's product cards, from rows
of comparison tables, and from the inline box's answer, with title, price,
rating and, where available, ASIN (from the card button, or from the product
link in the inline box). Cards that show no price have no button and thus no
ASIN in the page; they are recorded by title.

**Verified.** Replays of saved Amazon pages and live tests: all cards and table
rows captured once, with prices; ASINs for priced cards; no wrong ASIN for
tables with repeated IDs.

## 5. Assistant snapshots

**Problem.** `assistant_text` accounted for 90% of all recorded data. A snapshot
of the whole conversation was taken up to every 1.5 seconds while an answer was
being written, each ready-made question was stored four times with Amazon's
internal action code, products were stored three times, and every page change
resent the whole conversation. Pages where Amazon pre-renders its question
buttons produced snapshots although the assistant was never opened, so
"at least one snapshot" overstated assistant use.

**Change.**
- A snapshot is taken once the assistant's content has been unchanged for
  2.5 seconds (at the latest 15 seconds after a change), and immediately when
  the page is left or hidden, so the last state is not lost.
- Only conversation turns not recorded before in the session are sent;
  `turns_omitted` says how many known turns were skipped. A snapshot with
  nothing new is not recorded.
- Ready-made questions are stored once, as text (`suggested_question` blocks);
  other controls keep only their action type. Comparison tables are stored
  once (Amazon draws them twice).
- No snapshot without a question, a recommendation or an inline-box answer.
- The flattened `product_1_title` ... `product_5_brand` fields are removed.

**Verified.** Replays of saved Amazon pages in eight scenarios (existing
conversation, answer being written, leaving or hiding the page mid-answer,
assistant unused, each arm); live tests: no snapshot while the assistant was
unused, one per finished answer, a snapshot when leaving mid-answer. A
comparable session dropped from about 145 KB to about 50 KB.

## Changes to the recorded data

| Event / field | v2.1.0 | v2.2.0 |
|---|---|---|
| `schema_version` | `"4"` | `"5"` |
| `add_to_cart_click` | Product-page button only | Also from search tiles and the assistant: `detection: "cart_count"`, `surface` (`search_results`, `assistant`, `frame`, `product_page`, ...), `cart_count_from`/`to`; `title` when no ASIN (table rows) |
| `decision_made` | Product-page button only | First add from any surface (same fields) |
| `assistant_query_submitted` | – | New: `query`, `via` (`typed`/`suggested`), `surface` (`panel`/`inline_widget`) |
| `assistant_history_query` | – | New: questions of an earlier conversation shown again; not use |
| `assistant_text` | Snapshot up to every 1.5 s, whole conversation | One per finished answer; only new turns (`turns_omitted`); block kinds `markdown`, `header`, `product` (with `external` for other shops), `suggested_question`, `cta`; inline-box answer as turn `dpx-rex-nile-inline-answer-text-container`; no `product_N_*` fields; `product_suggestions` = 10 most recent products |
| `session_summary` | – | New counts `assistant_query_count`, `assistant_history_query_count`; `assistant_interaction_count` now counts snapshots of the new kind |

**Measuring assistant use.** Use `assistant_query_submitted` (count of asked
questions, or at least one), not the number of `assistant_text` snapshots.
For v2.0.0 and v2.1.0 data, which have no question events, a snapshot whose
`user_texts` is not empty is the closest proxy; it includes earlier
conversations shown again.

**Recommended products per answer.** Each product appears in the turn of the
answer that showed it (`turns[].blocks[kind = "product"]`). A turn can be sent
again with changes (for example when an answer was captured while still being
written before the participant left the page); de-duplicate by session, turn
and product.

## Testing these changes

With the three arm links of an unused participant ID:

1. `chat`: search, open a product, **do not** open the assistant for 20 s
   (nothing assistant-related should be recorded). Then ask a question in the
   panel, click a ready-made question, ask another and leave the page while
   the answer is still being written. Add a product from an assistant card.
   On a product page, ask a question in "Looking for specific info?" and click
   a follow-up button under its answer.
2. `chat_no_guide`: open the assistant (the earlier conversation may show) and
   ask one new question.
3. `classic`: search and open a product; no assistant element should be
   visible.

Expected: each asked question once as `assistant_query_submitted` with the
right `via` and `surface`; earlier questions only as `assistant_history_query`;
the add with `surface: "assistant"`; no assistant events in `classic`.

## Known limitations

- Cards and table rows without a price carry no ASIN in the page (title only);
  table rows lose their ASIN when Amazon repeats one ID across the table.
- After going back to a page, `cart_count_from` on the next add can be out of
  date (the add itself is correct).
- Text fields such as `brand` and `title` are recorded as displayed by Amazon
  and need cleaning in analysis.
- No `session_summary` is written when a participant abandons the task without
  confirming or stopping it; the one-hour cap ends recording.
